# Croniter upgrade: Zurich's repeated hour

Updating the same cron library can change its occurrence stream. This example
compares croniter **6.0.0** with **6.2.4** for `*/5 * * * *` in
`Europe/Zurich`, using tzdata **2026.2** on both sides.

## Upstream observation and controlled comparison

In [croniter issue #56](https://github.com/pallets-eco/croniter/issues/56), the
author sets an iterator's current time to `2023-10-29T02:55:00+02:00`, with
`fold=0`, then requests the next occurrence. The reported result jumps to
`03:00+01:00`, skipping the repeated hour after Switzerland's DST ends.

The [manifest](../examples/croniter-upgrade.json) compares the selected versions
through CronDelta's existing adapters in the inclusive/exclusive UTC window
**`[2023-10-29T00:55:00Z, 2023-10-29T02:10:00Z)`**. Both sides complete, with
identical timezone provenance and TZif SHA-256:

- croniter **6.0.0**: **3** occurrences; the repeated hour is skipped.
- croniter **6.2.4**: **15** occurrences, including twelve additional UTC
  instants in `[01:00Z, 02:00Z)` during the second local 02:00 hour.
- Verdict: **`DIFFERENT`**, first divergence at zero-based **index 1**.
  The older version yields `02:00Z`, local `03:00+01:00`, `fold=0`.
  The newer version yields `01:00Z`, local `02:00+01:00`, `fold=1`.

CronDelta's window includes the common first event at **`00:55Z`**, local
`02:55+02:00`, `fold=0`. Its adapter starts at the preceding whole UTC minute,
whereas the upstream example sets the current time to that event and calls the
exclusive `get_next()`. The witness therefore concerns the event *after* the
included `00:55Z`, rather than a difference at the initial boundary.

The second manifest case uses the same expression and UTC window with timezone
**UTC**. Both versions complete with **15** events and
**`MATCH_WITHIN_WINDOW`**, providing a control without a DST transition.

The [representative report](../examples/reports/croniter-upgrade.json) is a
schema-version-1 evidence collection generated by `scripts/reproduce.py`.
It records actual library versions, Python runtimes, interpreter paths, counts,
completeness, timezone provenance, and the bounded witness/context.

## Reproduce the comparison

From a checkout, prepare the locked development environment with
`uv sync --locked`. It supplies croniter 6.2.4 and tzdata 2026.2. Prepare the
existing historical dependency set in a disposable directory:

```sh
scratch=$(mktemp -d)
trap 'rm -rf "$scratch"' EXIT
runtime=$(uv run --no-sync python -c 'import sys; print(sys.executable)')
uv venv --python "$runtime" "$scratch/historical"
uv pip install --python "$scratch/historical/bin/python" \
  croniter==6.0.0 APScheduler==3.11.2 tzdata==2026.2
uv run --no-sync python scripts/reproduce.py \
  --manifest examples/croniter-upgrade.json \
  --left-python "$scratch/historical/bin/python" --right-python "$runtime" \
  --left-version 6.0.0 --right-version 6.2.4 \
  --output build/reports/croniter-upgrade.json
CRONDELTA_HISTORICAL_PYTHON="$scratch/historical/bin/python" \
  uv run --no-sync pytest -q tests/test_case_study.py -k croniter_upgrade
```

The helper's interpreter arguments override the manifest's default interpreter;
both versions must already be installed. `compare` performs no installation.
The output goes to the ignored `build` directory, leaving the representative
report intact. Absolute interpreter paths and runtime versions reflect the
actual run and may differ on another machine; they are not edited out of reports.

`sh scripts/verify.sh` prepares the historical interpreter and runs both new
regression cases, the reproduction command, and all existing package/migration
checks. A plain pytest run without `CRONDELTA_HISTORICAL_PYTHON` skips the
historical version tests.

## Evidence boundaries

This is a controlled comparison of the two chosen versions using one timezone
database, not a recreation of the issue author's complete environment. It
does not establish which release first changed this behavior or identify a new
upstream bug. It checks trigger calculations through croniter's public API,
not job execution by a complete scheduler. The UTC control establishes equality
only within its checked window.
